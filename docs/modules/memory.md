# 记忆模块：存储、检索与维护边界

状态：设计已确认，实施中。核对日期：2026-10-23。

## 当前实现与下一步边界

`MemoryStore` 目前同时拥有 SQLite 连接与迁移、记忆记录、向量缓存、候选查询、检索排序、观察合并、失效与遗忘。对外隔离规则与记录生命周期已有离线测试。

后续拟分离纯数据模型、检索排序策略、维护策略与存储实现；MemoryStore 保留兼容门面。排序策略只接收候选记录、向量分数与参数，不访问数据库或模型。存储层负责候选范围与访问水位的写入，维护策略计算变化，存储层提交变化。

## 当前发现的设计冲突

同一源文件内存在不一致，且已核对在重构前提交 `edc82ca` 中同样存在：

- `memory.py` 顶部第 21–24 行明确说明：importance 用绝对 `importance / 10`，不进行候选集合内的归一化。
- `MemoryStore.retrieve` 第 409–413 行实际计算：对 importance 也执行候选集合内 Min-Max，再与 recency、relevance 相加。

两者会产生不同排序。比如 importance 为 5 和 6 的两条候选，在该维度上分别得到 0.5 / 0.6（绝对权重）或 0 / 1（当前代码）。候选重要性相同时，当前归一化分支将该维度全部设为 1。

## 已确认的评分基线

用户确认采用绝对重要性权重：importance 维度固定使用 `importance / 10`，不做候选集合内 Min-Max。新近性和相关性仍分别在过滤后的候选集合内归一化；保持置信度乘数、传闻跳数折扣、最后追加的当前对象加权以及稳定排序顺序。

| 选项 | 重构基线 | 影响 |
|---|---|---|
| A：保持实际代码 | 保留候选集合内 Min-Max，修正文档与注释 | 保持已有检索行为，适合本轮结构重构 |
| B：按文档意图修正 | 使用绝对 importance / 10，不再归一化此维度 | 属于检索行为变化，需要单独验证与更新基线 |

实施分成两次提交：先单独修正评分并用离线用例冻结新行为，再提取记忆模块内部职责。None / shared 查询范围、访问副作用、遗忘、证据保护和数据库格式保持兼容。
