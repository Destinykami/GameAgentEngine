# 正确性与可靠性加固计划

日期：2026-10-25。状态：**A–E 已实施并完成离线验收**。

本计划依据结构重构完成后的代码审查制定。审查时的代码基线为 `3d67e65`，本计划由 `164981a` 落盘。目标是解决已复现的记忆隔离、缓存更新、保存失败和直播数据遗漏问题，并建立可重复的离线验收入口。

## 1. 已有证据与范围

本次审查重新执行并通过：417 个 Python 离线测试、5 个前端测试、TypeScript 检查及 Vite 构建。真实模型探针已排除，浏览器 E2E 未在本次审查中重跑。构建存在大体积资源包提示，暂不作为本轮优先项。

以上是当前实现的问题或已保留限制，不据此断言它们由上一轮重构引入。测试通过说明现有断言成立，并不代表这些边界已正确覆盖。

### 固定约束

- 记忆继续使用 SQLite；检索重要性权重继续使用绝对 `importance / 10`。
- 保持对话、自治、反思各自的记忆可见性边界，以及未涉及问题的既有行为。
- 不恢复 `persona_agent` 或私有字段代理兼容层。
- 不调用真实模型 API、真实探针或在线评测；测试用替身和临时目录。
- 每个模块先更新设计蓝图，再修改实现；完成后单独提交 Git。
- 本计划包含缺陷修复带来的行为变化，不能全部标记为“行为等价重构”。实施时逐项记录变化；未决设计先询问用户。
- 本轮不增加新玩法、调整模型提示词、引入向量数据库、并行模拟或优化真实模型效果。

## 2. 实施顺序与交付物

建议顺序：**A 记忆隔离 → B 信任缓存 → C 保存与恢复 → D 直播读取 → E 自动验收**。每阶段有独立验收和提交；C 的未决设计不阻塞其他阶段的独立工作。

### A. 修复共享流观察去重

目标：去重只能发生在同一记忆流内，共享观察不能被私人关系观察吸收。

修改范围：

- 蓝图：`docs/modules/memory.md`、`docs/modules/npc-runtime.md`。
- 实现：`src/game_agent/memory/store.py`；核对 `repository.py` 和 `cognition/npc/observation.py` 的调用契约。
- 测试：`tests/test_shared_stream.py`、`tests/test_obs_dedup.py`、必要的 NPC 组件测试。

执行步骤：

1. 写清查询语义：记录的 `player_id=None` 表示共享流；查询的 `all_valid(None)` 表示全部流；共享查询必须显式限定。
2. 先增加失败回归用例，证明“私人观察 → 同文共享观察”被错误合并。
3. 在观察去重边界把共享查询限定为共享流；保留 `all_valid` 的现有公共查询含义，避免影响维护和全量检索。
4. 检查去重窗口、合并来源、反思累积是否在正确流上执行。
5. 记录更广泛的显式查询对象方案，但本阶段不为单点修复迁移所有查询接口。

验收标准：

- 私人 → 共享、共享 → 私人、A 玩家 → B 玩家：相同内容都生成独立记录。
- 共享 → 共享、同玩家 → 同玩家：继续合并并保留原 ID、强化时间窗和来源升级规则。
- 写入共享观察不改变私人记录的内容、来源、重要性或访问时间。
- 新增共享观察正确驱动自我反思累积；私人观察不参与该累积。
- 既有对话隔离、共享反思、去重及绝对重要性测试通过。

建议提交：`fix(memory): 限定观察去重的共享流与关系流边界`。

### B. 让信任缓存跟随实际证据更新

目标：模型判断所依据的证据发生变化后，下次查询重新判断；仅重要性衰减不导致重新判断。

修改范围：

- 蓝图：`docs/modules/reaction.md`；必要时同步 `docs/modules/memory.md`、`docs/modules/npc-runtime.md`。
- 实现：`cognition/reacting/trust.py`；检查 `cognition/npc/reactions.py` 的完整决策缓存是否掩盖更新。
- 测试：`tests/test_reaction_components.py`、`tests/test_react_cache.py`、来源合并相关测试。

建议设计：保持缓存归属在 `RelationshipTrust`，基于实际送入模型的有序证据构建不可变签名，包含内容、置信度和传闻标记。保持高阶最多 10 条、观察最多 20 条的选择规则。优先复用当前读取结果，不为本次修复新增跨模块可变计数器。

执行步骤：

1. 增加传闻转亲见、内容补充、置信度变化、失效后同数量替换等回归用例。
2. 让签名与实际模型输入对应；同一证据输入应命中缓存。
3. 更新原来锁定“不随内容变化刷新”的行为保持测试，并在蓝图中说明修复理由。
4. 检查信任更新后完整反应缓存的结果：当前信任按 0.5 分桶，桶内变化仍可能复用旧效用。单独记录并决定其契约，不能只验证信任接口。

验收标准：

- 证据内容、置信度、亲见/传闻来源或入选顺序改变后重新调用模型。
- 相同输入重复查询不增加模型调用；仅 importance、访问时间变化不使信任缓存失效。
- 不同对象、不同 NPC 的缓存继续隔离；失败结果不写入缓存。
- 用 NPC 公开入口验证观察合并 → 信任查询 → 事件反应的完整路径。

已确认并实施：完整反应缓存按实际信任值更新，取消分桶近似；使用完整计划和人格的结构化键，下层评分同步区分人格。

建议提交：`fix(reaction): 按实际关系证据更新信任缓存`。若决定修改完整反应缓存，另立提交并说明行为变化。

### C. 明确保存失败与一致恢复契约

目标：先消除“未完整保存却显示成功”，再依据明确设计提供可恢复的一致检查点。

修改范围：

- 蓝图：`docs/modules/persistence.md`、`docs/modules/npc-runtime.md`、`docs/modules/scenarios.md`。
- 实现：`world/runtime.py`、`world/persistence.py`、`cognition/npc/persistence.py`，以及需要传播保存结果的运行器。
- 测试：世界/NPC 持久化、错误隔离与运行器相关测试。

C1：失败可见性，先做边界清晰的小改动。

1. 定义失败结果包含的 NPC 名称、阶段和异常原因。
2. 选择抛出明确异常或返回结构化结果；运行器不能在失败时打印保存成功。
3. 覆盖第一个/中间/最后一个 NPC 失败，以及世界库提交失败。
4. 明确声明：报告失败或回滚世界库，不等于回滚已经提交的 NPC 库。

C2：一致检查点，先设计后实现。

1. 明确恢复对象：世界、NPC 元数据、记忆记录，以及影响续跑的必要配置和状态。
2. 区分运行中的实时数据库和可发布检查点；因为记忆随观察即时写库，仅给 `save()` 增加事务无法恢复整次运行的一致性。
3. 建议评估“独立检查点目录 + 清单 + 完整写入后发布”，保留上一份完整检查点；实施前评估空间和复制成本。
4. 用故障注入验证中途中断不会让恢复入口选择半成品。

用户已确认并实施：保存失败明确抛错，由运行器终止；检查点用于继续游戏进度，不承诺模型输出逐字相同；接受独立代目录和额外磁盘副本。旧数据库继续经原 save/load 使用，完整检查点通过新增入口显式恢复。

验收标准：C1 必须准确报告部分失败；C2 必须保证恢复使用同一代检查点，并覆盖 NPC 写入失败、世界写入失败、清单发布前中断。C1 完成不能标记为 C2 已完成。

建议提交：分别为 `fix(persistence): 显式报告不完整保存` 与 `feat(persistence): 发布并恢复一致检查点`；具体拆分依据确认后的模块设计。

### D. 修复直播读取与重试

目标：解析失败不跳过尚未成功处理的步骤，轮询重叠不造成乱序或重复初始化。

修改范围：`docs/modules/visualization.md`、`visualization/src/data/liveSource.ts`、`visualization/src/replay/LivePlayback.ts`、`visualization/tools/test_replay.ts` 及必要的浏览器夹具。

执行步骤：

1. 游标只推进到成功处理的完整行；保留尾部半行在下一轮重试。
2. 增加“坏行修复后恢复摄入”的回归测试，替换原来保留跳行行为的断言。
3. 通过单次在途轮询约束，覆盖网络请求或资源初始化超过轮询周期的情况。
4. 文件截断和新运行切换需要显式策略；不通过行数减少猜测并悄悄拼接两次运行。

验收标准：

- 重复轮询不重复追加；半行补全后恰好追加一次。
- 中间坏行不导致后续步骤永久遗漏；修复后顺序摄入并识别结束标记。
- 404、请求失败不推进游标；慢请求不重复建立场景。
- 当前样本与历史样本均通过回放验证；直播跟随和结束状态通过浏览器检查。

已确认并实施：坏行阻塞并显示错误，修复后原位重试；新运行通过 run_id 和已消费前缀识别，提示重新加载，不自动混合。

建议提交：`fix(replay): 保留直播失败位置并串行摄入数据`。若引入新运行标识，需要运行器和回放共享协议设计并独立提交。

### E. 固化离线验收与模块边界

目标：默认测试无真实网络依赖，提交后可以稳定重复检查模块边界与行为。

修改范围：`pyproject.toml`、`tests/test_probes.py`、必要的 `tests/conftest.py`、`tests/test_module_dependencies.py`、前端测试脚本和文档。根据仓库托管环境选择 CI 配置。

执行步骤：

1. 给真实端点测试增加显式开关，默认不探测连通性；单独指定探针文件也必须尊重开关。
2. 离线测试增加真实外部 HTTP 访问拦截，同时允许替身及测试需要的本地服务。
3. 在现有导入隔离测试之外，增加核心层不能反向依赖具体场景或运行器的检查。
4. 建立统一验收入口：后端离线测试、前端测试、TypeScript/Vite 构建、时间线校验。
5. 浏览器 E2E 作为较重的独立检查；增加 wheel 独立安装检查，避免源码路径掩盖打包缺漏。

验收标准：普通测试在 API 不可达时不等待探针；在线测试必须主动开启；核心逆向依赖能够被检查发现；独立安装可导入正式公共 API。

建议提交：`test: 默认离线验收并检查模块依赖边界`。若增加托管平台 CI，再单独提交配置。

3. 先运行相关模块测试；阶段完成时运行后端离线全量测试。前端变更运行前端测试、构建和相关浏览器检查。
4. 不盲目要求修复后的所有产物与旧版逐字一致；为批准的行为变化列出预期差异，其余路径继续回归验证。
5. 提交正文记录问题、模块边界、行为变化、验证结果和未运行项；仅提交本阶段文件。
6. 回填本计划中的真实提交哈希和验收结果，不把建议提交名当成已完成记录。
